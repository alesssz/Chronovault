- **Coverage floors** (`coverage.thresholds` in `vitest.config.ts`): `pnpm test:coverage`, run by `pnpm check` / `make check` and by CI, fails when a folder's coverage drops below its floor, naming the folder, the measure and both numbers. Only the folders whose main guard is the unit tests have one; each floor is the folder's coverage when it was set, rounded down:

  | Folder | Lines | Statements | Functions | Branches |
  |---|---|---|---|---|
  | `shared/` | 100 | 99 | 100 | 97 |
  | `server/services/` | 96 | 95 | 95 | 89 |
  | `server/mappers/` | 100 | 92 | 100 | 80 |
  | `app/lib/` (the player's logic included) | 76 | 74 | 74 | 70 |
  | `app/stores/` (the player store) | 94 | 93 | 94 | 85 |

  Routes (`server/api/`), repositories, components, pages and composables have none: Playwright covers them end to end, and this report counts Vitest only (the whole project shows about 42% of lines, far below what the tests really exercise). New code in a guarded folder comes with its tests, or the floor stops it. **Raise a floor** when tests raise its folder's coverage (the terminal shows only the totals; open `coverage/index.html` for each folder and file); **never lower one** to let a change through, unless code was moved out on purpose, and then say so in the commit.
- E2E tests generate WAV files on the fly and register throwaway users (`e2e-…@chronovault.test`) in the local database; they do not touch your own data.
- **Never assert on wall-clock time.** A check like "no progress toast appears for a fast download" must not depend on how fast the runner is: the download test stops the page's clock (`page.clock.install()`, then `pauseAt`) for the download, then moves it on past the toast's 700 ms (`runFor`), so it checks the logic (the timer is cleared when the download ends) and nothing else. It used to fail on a slow runner for a download that is fast for any user. Where the point is that something happens without waiting, assert the order of events instead of a duration: the track-change test checks that no request for the next track goes out between the end of one track and the start of the next, where it used to require a gap under 250 ms.
- **Wait for the server, not for a toast, before relying on a save.** A success toast stays on screen for a few seconds, so after a second save with the same message ("Changes saved", "Cover updated") the toast assertion passes before the request has finished. `clickAndWaitForApi(page, control, { method, path })` (`test/e2e/helpers.ts`) clicks and waits for that request's successful response.
- **Many tracks: `seedLibrary(page, count)`** (`test/e2e/helpers.ts`) makes them through the API, a tiny WAV each, ten at a time ("Track 001", "Track 002"…): hundreds take seconds, where uploading them through the page would take minutes. Use `uploadTrack` when the upload itself is under test.
- **Component tests boot Nuxt once per file** (a `beforeAll` hook of `@nuxt/test-utils`): a few seconds on an idle machine, but past Vitest's default 10 s on a busy one, where every file in `test/nuxt/` failed with `Hook timed out in 10000ms`. `vitest.config.ts` gives that hook 60 s (`hookTimeout`, `nuxt` project only).
- **Specs import `test` and `expect` from `./fixtures`, not `@playwright/test`.** The extended `test` fails a test when the browser reports something blocked by the Content Security Policy ([8.5](08-data-model-and-security.md#85-security-guarantees)): a missing origin throws nowhere in the app's code (the audio just never plays, the upload hangs), so every flow doubles as a check of the policy. It watches the test's own context and every context the test opens with `browser.newContext()`, the anonymous visitors of the share pages included. `security-headers.spec.ts` checks the headers themselves, and is skipped with `E2E_DEV=1` (the dev server sends no policy).
- **A test that plays a track and then works on the queue uses long tracks** (`uploadTrack(page, title, { seconds: 120 })`). The default WAV lasts 3 seconds, which suits a test that waits for a track to end (repeat, the next track starting); in any other test a track can end mid-way on a slow runner and move the queue on by itself (the editable-queue test failed on CI that way: Up next was empty right after a removal).
- pgTAP tests run inside a transaction that is rolled back: they never change the database.
- **Projects:** `chromium` (desktop) runs every spec except `responsive.spec.ts`; `phone` (Pixel 7 emulation) and `tablet` (820×1180, touch) run only that one, since the other specs drive the desktop layout. Run a single one with `--project phone`.
- Locally Playwright reuses a server already running on :3200 — stop it first, or it may test an old build.
- **CI** (`.github/workflows/ci.yml`) runs on **every push to any branch** ([14.1](14-conventions.md#141-git-workflow)), with a read-only token; a new push cancels the run still going on the same branch, never on `main`. Job 1 runs lint, typecheck and Vitest with the coverage floors (`pnpm test:coverage`); job 2 starts a trimmed Supabase in the runner and runs the schema checks, each failing the run (`db:lint --fail-on warning`: the SQL functions' types; `db:advisors`: Supabase's security and performance advisors; `db:types:check`: the committed TypeScript types against the migrations), then pgTAP and Playwright, uploading the report on failure. Playwright's headless Chromium (`--only-shell`: the tests never open the full browser) is cached between runs, keyed on the Playwright version; the system libraries it needs are installed on every run. A second workflow, `.github/workflows/audit.yml`, audits the dependencies every Monday and on any push, to any branch, that changes them, so before the merge too ([11.6](11-local-development.md#116-updating-dependencies)).
